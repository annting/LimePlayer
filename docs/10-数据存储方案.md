# 10 · 数据存储方案（播放记录 / 观看历史 / 新增媒体）

> **状态**：设计稿（2026-10-27）；**P0 已于 2026-10-28 实施并在三星真机验证通过**（见 §14 落地记录）。
> **范围**：本期只落 **SMB 文件源**、且**只处理视频文件**（音频不纳入，见 D7）；但数据模型按「文件型源」抽象，本地视频（`SourceType.LOCAL`）接入时**不加表、不改主键**。
> **依赖文档**：`02-技术规范.md` §4 领域模型 / §7 本地缓存、`08-SMB源实现方案.md` §2.7、`07-问题排查.md`。
> **本文件与之冲突时**：§7 本地缓存结构以**本文件**为准（新增的表在 `02` 里只有一句话，没有字段级定义）。

## 1. 结论先行

| # | 决策 | 一句话理由 |
|---|---|---|
| **D1** | **进度落库由播放层统一写，不再由各源自己存** | 现状是「源各自上报」：Emby 报服务端、SMB 空实现 → 进度天然只有在线源有。改为「播放层写本地库 + 源只负责上报远端」，SMB / 本地 / 未来 WebDAV 零成本获得进度能力，且 `:source:*` 不必依赖数据库 |
| **D2** | **文件型源单独开表（`file_media_items`），不动现有 `media_items`** | 现有表是 Emby 形状（`seriesName/season/episode/communityRating…`），文件源需要的是 `path/size/mtime/firstSeenAt/kind`；混一张表会一半字段恒 null，且现有查询与 20 条测试要全改 |
| **D3** | **本地进度必须独立成表，不能复用 `media_items.resumePositionTicks`** | 那两列是**服务端权威值**：每次 `syncItems` 都会用服务器返回覆盖（`RoomLibraryRepository.kt:41`）。拿它存本地进度，一次同步就被抹掉 |
| **D4** | **主键用「源 + 相对路径」，不用现有的 Base64 itemId** | SMB 的 `itemId` 是路径的 Base64（`SmbMediaSource.kt:73`），本地源将来可能是 `content://` URI 或 MediaStore id —— 身份规则会随源演化。路径是文件源唯一稳定、可读、可迁移的身份 |
| **D5** | **「昨日新增」不建汇总表，靠 `firstSeenAt` 实时查** | 数据量是万级、按日查一次，物化表只会带来一致性负担。关键是 `firstSeenAt` 必须**只写一次**（`@Upsert` 会覆盖，见 F3） |
| **D6** | **技术信息（时长 / 分辨率 / 编码）探一次就入库**，详情页不再实时读文件头 | 现状是每次进详情都 `MediaExtractor` 现探（`SmbMediaSource.probeMedia` 只有 200 条内存 LRU，进程重启即丢）；而且 `resumeFraction()` 依赖时长（F5），不入库连进度条都画不出来。用户 2026-10-27 明确要求「获取一次存入数据库」 |
| **D7** | **本期完全不纳入音频**：不扫音频扩展名、不入库、不统计、不展示 | 用户 2026-10-27 决定「暂时不考虑兼容音频格式」。所以 §2.2 的「只认 14 种视频扩展名」**保持不变**，`AudioExtensions` 不扩、§12 的音频期整体移出排期。表结构里的 `kind` 列与 `MediaKind.AUDIO` 枚举值**保留但本期恒为 `VIDEO`** —— 加一列/加一个枚举值的成本为零，将来接音频时不必做数据库迁移 |

## 2. 现状盘点（写方案前的事实基线）

### 2.1 现有 Room

| 项 | 现状 | 证据 |
|---|---|---|
| 数据库 | `myplayer.db`，**version = 1**，只有 2 张表 | `MediaDatabase.kt:6-16` |
| 表 1 | `libraries(serverId, libraryId)` —— 服务端库清单 | `Entities.kt:6` |
| 表 2 | `media_items(serverId, itemId)` —— 服务端条目缓存（28 列） | `Entities.kt:15-51` |
| schema 导出 | **`exportSchema = false`**（M1 未发布时的选择） | `MediaDatabase.kt:11` |
| 迁移 | builder **没有 `.fallbackToDestructiveMigration()`**，也没有任何 `Migration` | `AppModule.kt:43-44` |
| 写入者 | 只有 `RoomLibraryRepository`（`syncLibraries` / `syncItems` / `updateUserData` / `deleteItem`） | `RoomLibraryRepository.kt` |

> **直接后果（F1）**：现在往数据库加任何表，**必须同时写 `Migration(1, 2)`**。没有 fallback，升级会直接 `IllegalStateException` 崩在启动。而 `exportSchema=false` 又没法用 `MigrationTestHelper` 做迁移测试 —— 所以本期第一步是**把 schema 导出打开并把 v1 基线导出来**。

### 2.2 现有口径（改动必须遵守）

| 口径 | 规则 | 出处 |
|---|---|---|
| 时间 | 领域层一律 `Ticks`（100ns）；Room 边界显式转 `Long` | `Ticks.kt`、`Mappers.kt:1-8` |
| 播放位置 | 播放层用 `Duration`（ms），`MediaSource.reportProgress` 收 ms | `MediaSource.kt:16-31` |
| `path` | **「详情专属字段：只在 getItemDetail() 填充、不同步入库」** | `Models.kt:57-62` |
| `userData` | `isPlayed` / `resumePositionTicks` 是**服务端权威值**，本地只做缓存 | `Daos.kt:40-51` |
| 条目 id | SMB = `Base64Url(相对路径)`，可逆（`decodeId`） | `SmbMediaSource.kt:67-79` |
| 文件类型 | SMB 只认**视频**扩展名（14 个），**没有音频** —— **本期保持现状**（D7） | `SmbConfig.kt:80-90` |

> **本期新增口径**：新增表一律**用 ms 存时长/位置**（`Long`），只在与 `MediaItemDto` 交界处换算成 `Ticks`。理由：文件源没有 tick 概念，播放层本来就是 ms；统一成 ms 后 SQL 里做「昨日新增时长」「剩余时长」不用乘除 10^7。

### 2.3 缺口清单（本期要补的）

| 缺口 | 现状 | 影响 |
|---|---|---|
| 播放记录 | 无表；SMB 完全不记 | 退出即丢，重进从头播 |
| 观看历史 | 无表 | 无「最近看过」、无法按日统计 |
| 新增媒体 | 无「首次发现时间」概念，只有文件 `mtime` | 无法回答「昨天新进了哪些片子」 |
| 音频 | 扫描直接过滤掉非视频文件 | **本期不做**（D7）：不纳入即无缺口；`kind` 列留好，将来接音频不改表 |
| 技术信息（分辨率/编码/时长） | 现场探测、LRU 200 条内存缓存，**不入库** | 每次进详情重读文件头；页面之间不共享 |
| SMB 已看标记 | `SmbVideoItem.watched` 只是内存态（刷新即丢） | 多选「标记已看」看起来生效、重进就没了 |

## 3. 此前调查结论归档（SMB 播放进度丢失）

> 这一节是为了让后面所有设计决策**有据可查**，不必再翻聊天记录。结论来自 2026-10-27 的专项排查（当时明确不改代码）。

### 3.1 五层链路诊断

| 层 | 现状 | SMB 结果 | 证据 |
|---|---|---|---|
| ① 触发时机 | 齐全：状态跃迁 + 每 10s + 退页补报 | ✅ 照常触发 | `ProgressReporter.kt:40,52`、`PlayerViewModel.kt:531-547` |
| ② 退页回调 | `leave()` → pop → `onCleared()` 补报 STOPPED | ✅ 照常执行 | `PlayerRoute.kt:91-102` |
| ③ 上报交付 | `reportProgress` **空实现** | ❌ **断点** | `SmbMediaSource.kt:175`（`= Unit`） |
| ④ 持久化 | 播放链路**没有任何写库入口** | ❌ 无 | 全仓 `updateUserData` 只被详情页「标记已看」调用 |
| ⑤ 回读 | 续播列表 / 详情断点 / 卡片进度 | ❌ 三处全无 | `SmbMediaSource.kt:188,115-133`；`SmbVideoCard` 无进度条 |

### 3.2 根因（R1–R5）

- **R1（主因）上报是空实现**：10s 周期、暂停、退页 STOPPED 全部落到 `= Unit`。类注释也写着「不支持的能力…续播上报」（`SmbMediaSource.kt:41`）。
- **R2（结构性）没有本地进度存储**：`SmbProgressStore`（`filesDir/smb_progress_<id>.json`）**只存在于 `docs/08 §2.7`，代码里不存在** → 属 P0 未完成项，**不是回归**。
- **R3（回读缺失）**：`getResumeItems()` 恒空（首页「继续观看」被隐藏）、`toDto/getItemDetail` 不带断点（详情页永远 0 起点）、`PlayerViewModel` 用 `userData.resumePositionTicks` 起播（`:232`）。
- **R4（触发时机的边角）**：
  | 缺口 | 机制 | 后果 |
  |---|---|---|
  | 连播不停旧 reporter | `start()` 每次新建 reporter 挂同一 `viewModelScope`，无 `stop()`（`:246`） | 旧条目会被新会话的位置持续上报（污染上一集断点） |
  | 起播未完成就退出 | `sessionItem` 在 `getItemDetail` 成功后才赋值（`:244`） | 快速返回时连 STOPPED 都不发 |
  | 进程被杀 | `onCleared` 补报是 `GlobalScope` fire-and-forget（`:538`） | 最多丢 10s；SMB 全丢 |
  | 缓冲期 | `toPlayState()` 对 `IDLE/BUFFERING` 返回 null + 周期上报带 `isPlaying` 守卫 | 长缓冲期间的位移不计 |
- **R5（可观测性）**：Emby 有 `LimeReport` 日志，SMB 连「尝试过上报」都看不到。

### 3.3 异常中断矩阵（SMB）

| 场景 | 触发点 | Emby 落点 | SMB 结果 |
|---|---|---|---|
| 播到中途返回 | `onCleared` → STOPPED | `/Sessions/Playing/Stopped` | 丢 |
| 播完 / 失败 | `ENDED/FAILED` → STOPPED | 同上 | 丢 |
| 切后台（默认暂停） | `pause()` → PAUSED | `/Progress` | 丢 |
| 后台被杀 | 无 `onCleared` | 靠 10s 兜底 | 全丢 |
| 连播换集 | 新旧 reporter 并存 | 双上报 | 丢 |
| 起播期退出 | 无上报 | 无 | 无（可接受） |

### 3.4 本轮设计评审新增发现（F1–F7）

| # | 发现 | 证据 | 对方案的影响 |
|---|---|---|---|
| F1 | 加表必须写 `Migration(1,2)`，且 `exportSchema` 要先打开 | `MediaDatabase.kt:11`、`AppModule.kt:44` | §9 迁移方案 + 先决条件 |
| F2 | `MediaItemEntity` **没有 `path` 列**；`path` 被定义为「不同步入库」 | `Entities.kt` 全表、`Models.kt:57-62` | D2/D4：文件源必须有自己的表存 path；不能指望现有表 |
| F3 | `@Upsert` 会覆盖已有列 → `firstSeenAt` 会被重扫抹掉 | `Daos.kt:21` | §6.3 规定「插入用 `INSERT OR IGNORE`，更新走显式 UPDATE 白名单」 |
| F4 | `planPlayback` 的路径兜底是 `item.path ?: item.id` | `SmbMediaSource.kt:168` | 从 Room 直接拿到的条目（path=null）会把 Base64 当路径 → stat 失败。建议顺手改成 `item.path ?: decodeId(item.id)`（1 行，非本期必需） |
| F5 | `resumeFraction()` 依赖 `durationTicks`，而 SMB 列表接口不带时长（`durationTicks=0`，只有详情页 probe 才有） | `Models.kt:104-108`、`SmbMediaSource.kt:115-126` | **进度条要显示，时长必须入库** → 本期把 probe 结果持久化（§6.4） |
| F6 | `getResumeItems()` 空 → 首页「继续观看」模块被 `hasContent` 逻辑隐藏 | `SmbMediaSource.kt:188`、`HomeScreen.kt:328` | 本期改成「从本地表组装」 |
| F7 | 扫描层只有 `VideoExtensions`，音频扩展名不存在 | `SmbConfig.kt:80-90` | **不修**：D7 决定本期不纳入音频，扩展名表保持 14 项；§6.3 的 `kind` 列只作预留 |

### 3.5 与 `docs/08 §2.7` 的关系

`08` 的原设计是「SMB 源内部写一个 JSON 进度文件，`getItemDetail` 合并」。本方案**取代**它：

- 保留「合并进 `userData.resumePositionTicks`」这个**读出口**（这样详情页/首页/库页零改动）；
- 但**写入方从源挪到播放层**（D1），存储从 JSON 换成 Room（可查询、可按日统计、能与观看历史共用事务）；
- 原因是 JSON 方案解决不了「观看历史」「昨日新增」「跨源统一」这三件事，而且每个新源都要再实现一遍。

## 4. 目标 / 非目标

**目标**

1. 播放中途退出（含异常路径）**必定**留下断点；重进可续播。
2. 有完整的观看历史（每次会话一条事实记录），支撑「最近看过 / 按日统计」。
3. 能回答「昨日新增了哪些**视频**」，且口径稳定（不因重扫而漂移）。
4. 技术信息（时长/分辨率/编码）入库一次，详情页不再反复读文件头。
5. SMB 与将来的本地视频**共用一套表与一套读写路径**。

**非目标（本期不做）**

- **音频完全不纳入**（用户 2026-10-27 决定「暂时不考虑兼容音频格式」）：不扫音频扩展名、不入库、不统计、不展示、不播放。NAS 上的 mp3/flac/m4a 在应用内**不可见**，这是明确接受的取舍，不是缺陷。表里的 `kind` 列与 `MediaKind.AUDIO` 仅作将来扩展的预留位（本期恒 `VIDEO`）。
- 跨设备/云端同步（纯本地库，重装即丢）。
- Emby / Jellyfin / 飞牛的**本地进度反向同步**（它们继续用服务端权威值，本地表只做兜底与历史）。
- 缩略图/海报缓存策略（另有 `LocalThumbnailProvider` 的 LRU，本期不动）。

## 5. 统一数据模型抽象

### 5.1 分层

```
        ┌───────────── 播放页 / 首页 / 库页 / 详情页（feature:*）
        │  只依赖接口：PlaybackStore / MediaCatalog
        ▼
┌───────────────────┐   ┌──────────────────────┐   ┌───────────────────┐
│ MediaSource（现有）│   │ MediaCatalog（新）    │   │ PlaybackStore（新）│
│ 远端：列库/列条目   │   │ 文件型源的清单/属性    │   │ 进度 + 历史 + 统计 │
│ 上报：Emby/Jellyfin │   │ SMB: smbj · LOCAL: SAF│   │ 实现：Room         │
└─────────┬─────────┘   └──────────┬───────────┘   └─────────┬─────────┘
          │                        │                          │
          ▼                        ▼                          ▼
   远端服务器 / 文件共享   ┌─────────────────┐          ┌──────────────┐
                          │ FileLocator     │          │  Room (v2)   │
                          │ SMB / FILE / SAF│          │ 5 张表        │
                          └─────────────────┘          └──────────────┘
```

三个新接口的分工（关键：**谁都不依赖谁**）

| 接口 | 职责 | 谁实现 | 谁调用 |
|---|---|---|---|
| `MediaCatalog` | 「文件型源里有什么」：`scan(scope)` → `Flow<MediaEntry>`、`stat(path)`、`resolvePlayable(entry)` | `:source:smb`（本期）、`:source:local`（后续） | 库页 / 首页 / 详情页 |
| `PlaybackStore` | 「看过什么 / 看到哪」：`recordPosition` / `beginSession` / `endSession` / `observeContinueWatching` / `newlyAdded(day)` | `:core:database`（唯一实现） | 播放页 / 首页 / 详情页 |
| `MediaSource` | 现有契约，**不变**（Emby 仍走它上报服务端） | 三个在线源 | 现有页面 |

> **D1 的落地含义**：`PlaybackStore.recordPosition(...)` 由 `PlayerViewModel` 调，**不经过** `MediaSource`。`MediaSource.reportProgress` 继续存在，只服务「远端服务器」（Emby/Jellyfin/飞牛）；SMB 保持空实现并标注「本地进度由 PlaybackStore 负责」，不再是一个"坑"。

### 5.2 身份规则（最重要的一条）

```
mediaKey = "<sourceId>/<相对路径>"          // 例：srv_a1b2/Movies/沙丘.mkv
sourceId = ServerConfig.id（SMB）| "local"（本地单根，多根时为 "local:<根序号>"）
```

| 规则 | 说明 |
|---|---|
| 存**相对路径**而不是绝对路径 | SMB 换 IP / 换端口 / 换挂载点后进度不能丢 |
| 大小写敏感 | SMB 共享在 Linux 端大小写敏感，不做归一化（只在查询时可选 `COLLATE NOCASE` 做匹配，不用于主键） |
| 分隔符统一 `/` | 本地 `File.path` 在 Android 上本来就是 `/`；Windows 侧 SMB 也按 `/` 归一 |
| 不把 Base64 id 当主键 | 仅作为 UI/路由 id，需要时由路径重算（`encodeId`） |
| 重命名 = 新条目 | 旧记录成孤儿，由 §8 的清理任务回收（不做"智能跟随"，成本远大于收益） |

### 5.3 统一条目模型（SMB / LOCAL 共用）

```kotlin
// 伪代码：领域模型草案，落点在 :core:model（不是实现）
enum class MediaKind { VIDEO, AUDIO }   // 本期只产出 VIDEO（D7）；AUDIO 是零成本的预留值

data class MediaEntry(
    val sourceId: String,
    val path: String,              // 相对源根
    val kind: MediaKind,
    val name: String,              // 含扩展名
    val title: String,             // 去扩展名
    val sizeBytes: Long,
    val fileModifiedAt: Long,      // 文件自身时间（SMB: LastWriteTime；LOCAL: lastModified）
    val firstSeenAt: Long,         // 本机**首次发现**时间（只写一次，见 D5/F3）
    val durationMs: Long?,         // 来自技术信息表（可空：未探测）
    val width: Int?, val height: Int?,
    val videoCodec: String?, val audioCodec: String?,
    val bitrate: Int?,
    val playable: Boolean,         // 能否直接播（SMB 看代理、LOCAL 看权限）
)
```

**为什么不再用 `MediaItemDto` 当存储模型**：那个类是「三源并集」，带 `seriesName/season/episode/communityRating/canDelete/people/mediaStreams` 等一堆文件源永远为空、或永远不入库的字段（`Models.kt:38-98`）。存储层用它 = 一半列是噪声。桥接只在出口做一次：

```
MediaEntry + PlaybackProgress  ──(adapter)──▶  MediaItemDto（userData 填断点）
```

这样一个 adapter 就让 **详情页、首页「继续观看」、库页进度条全部零改动**地跑在本地数据上。

### 5.4 `FileLocator`（SMB 与本地唯一真正需要分叉的地方）

```kotlin
sealed interface FileLocator {
    data class Smb(val share: String, val path: String) : FileLocator
    data class LocalFile(val absolutePath: String) : FileLocator
    data class SafDocument(val treeUri: String, val documentUri: String) : FileLocator
}
```

- 存 `media_sources.locatorType + locatorBase`，条目侧只存相对路径 → **换根目录才需要改源记录**。
- `resolvePlayable(entry)`：SMB → 起 `SmbStreamServer` 拿 `http://127.0.0.1`（现有实现）；本地 → 直接 `file://` 或 `content://`（ExoPlayer 原生支持，不必走代理）。**这条分叉必须留在 catalog 层，播放层不许感知**。

## 6. 表结构设计

### 6.1 ER 概览

```
media_sources 1 ──── n file_media_items 1 ──── n media_streams(P1)
                           │ 1
                           │
                           ├──── n watch_history        （事实表，append-only）
                           └──── 1 playback_progress    （汇总表，每条目一行）

media_items / libraries（现有，服务端源，本期不动）
```

> `watch_history` / `playback_progress` **不设外键**（跨源通用，且条目可能被删/改名）。用 `sourceId + mediaKey` 逻辑关联，冗余一列 `titleSnapshot` 保证历史可读。

### 6.2 `media_sources`（源注册表）

### 6.6 `watch_history`（观看历史：append-only 事实表）

| 列 | 类型 | 说明 |
|---|---|---|

| `kind` | TEXT | `VIDEO` / `AUDIO`（本期恒 `VIDEO`，同 D7） |
| `startedAt` | INTEGER | 会话开始 |
| `endedAt` | INTEGER | 会话结束（NULL = 未闭合，启动时修复，见 §8） |

| `durationMs` | INTEGER | |

| `playMethod` | TEXT | `DIRECT` / `TRANSCODE` / `PROXY`（SMB 恒 `PROXY`） |
| `endedReason` | TEXT | `USER_EXIT` / `ENDED` / `ERROR` / `APP_KILLED` / `UNKNOWN` |

```sql
CREATE TABLE IF NOT EXISTS watch_history (
  sessionId TEXT NOT NULL PRIMARY KEY,
  sourceId TEXT NOT NULL,
  mediaKey TEXT NOT NULL,
  titleSnapshot TEXT NOT NULL,
  kind TEXT NOT NULL,
```

**为什么历史要独立于进度**：进度是"当前状态"（可覆盖），历史是"事实"（不可改写）。一个条目可以有一条 progress、几百条 history。合并成一张表会导致「继续观看」每次都要聚合、且看不完的记录被下一次播放冲掉。

### 6.7 「昨日新增」：不建表，靠索引实时查

```sql
-- 昨日新增（按 kind 分组；本期只会返回 VIDEO 一行 —— 音频延后见 D7。时区按设备本地时区，见 §13）
SELECT kind, COUNT(*) AS count, SUM(sizeBytes) AS bytes, SUM(IFNULL(durationMs,0)) AS durationMs
FROM file_media_items
WHERE sourceId = :sourceId
  AND missingAt IS NULL
  AND firstSeenAt >= :dayStart AND firstSeenAt < :dayEnd
GROUP BY kind;

-- 昨日新增列表（含今天，用于「最近添加」模块的 N 天窗口，与现有设置兼容）
SELECT * FROM file_media_items
WHERE sourceId = :sourceId AND missingAt IS NULL AND firstSeenAt >= :sinceMs
ORDER BY firstSeenAt DESC LIMIT :limit;
```

> `:dayStart/:dayEnd` 由调用方用 `LocalDate.atStartOfDay(ZoneId.systemDefault())` 算好再传（SQL 里不存时区，避免"跨时区同一条记录算两天"）。

## 7. 读写路径与时序

### 7.1 扫描（谁写 `file_media_items`）

| 时机 | 动作 |
|---|---|
| 进入库页 / 下拉刷新 | 扫该顶层目录（`list()` 一层的现有行为），`INSERT OR IGNORE` + `UPDATE` 白名单，**同一事务**分批 200 条 |
| 全量扫描 | 扫完把 `lastSeenAt < scanStart` 的条目标 `missingAt`（不删），`media_sources.lastScanStatus=OK` |
| 扫描失败（SMB 断连） | `lastScanStatus=FAILED`，**不标 missing**（否则断网 = 全库消失） |
| 详情页进入 | 若 `probeState='NONE'` 则探测一次，把 `durationMs/width/height/videoCodec/audioCodec/bitrate` 写回条目行、`probeState='OK'` + `probedAt`；`UNSUPPORTED`（AVI 之类 `MediaExtractor` 读不出）同样落库，**下次不再重试**（D6） |

### 7.2 播放（谁写 `playback_progress` / `watch_history`）

| 时刻 | 动作 | 数据源 |
|---|---|---|
| 起播成功（首个 PLAYING） | `beginSession()` 写一条 `watch_history`（`endedAt=null`、`startPositionMs`） | `PlayerViewModel.start()` 成功后 |
| 播放中每 10s | `recordPosition(positionMs, durationMs)` 覆盖写 progress | 沿用 `ProgressReporter` 的节流节奏（不新增轮询） |
| 暂停 | 立刻 `recordPosition` | 状态跃迁，同现有 |
| 退页 / 播完 / 失败 | `endSession(reason, endPositionMs, completed)`：闭合 history + 更新 progress（看完则 `positionMs=0, completed=1`） | `onCleared` 现有的 STOPPED 补报点 |
| 进程被杀 | 无回调 → 靠"最近一次 10s"兜底；下次启动跑**未闭合会话修复**（§8） | 启动任务 |

> **R4 的两个窟窿在这里顺手补掉**：
> ① `onCleared` 除了写库，还要 `reporter?.stop()` 并保留"最后一次位置"快照（不再依赖 `_ui`）；
> ② `startNext()` 换集时先 `endSession(当前集)` 再 `beginSession(下一集)` —— 现在连播会让上一集一直挂着一个 reporter。

### 7.3 事务与幂等

- progress 写：`INSERT ... ON CONFLICT(sourceId, mediaKey) DO UPDATE`，天然幂等，重复调用无副作用。
- `endSession` 一个事务内做 2 件事（闭合 history + 更新 progress），避免"历史闭合了但断点没更新"。
- 扫描一个目录一个事务；**不要整库一个事务**（SMB 上万条目会让 UI 卡住且失败全回滚）。

### 7.4 依赖方向（不能反过来）

```
feature:player ──依赖──▶ core:model（接口 PlaybackStore）
feature:library ───────▶ core:model（接口 MediaCatalog）
core:database ──实现──▶ 两个接口（Hilt 绑定）
source:smb ─────实现──▶ MediaCatalog（**不碰 Room**）
```

`source:*` 不依赖数据库（现在也不依赖，保持）。这样 SMB 的 JSON 进度方案被彻底抛弃，也不会出现"每个源各写一遍本地进度"。

## 8. 一致性与清理

> **本期口径（用户 2026-10-27 拍板 ④「先一直保留」）**：下表里凡涉及**删除**的行 —— 文件消失后真删、孤儿进度清理、看完旧片删 progress、历史裁剪 —— **本期一律不执行**，只保留「写标记」的部分（`missingAt` / `endedAt` / `lastPlayedAt`）。这样将来上刷新/清理策略时依据齐全，也不必改表。唯一必须运行的是**未闭合会话闭合**（它不是删除，是补 `endedAt`，否则历史里永远挂着 `endedAt=null`）。

| 场景 | 处理 |
|---|---|
| 未闭合会话（进程被杀） | 启动时 `SELECT * FROM watch_history WHERE endedAt IS NULL`：用该条目的最新 progress 补 `endPositionMs` + `endedAt`，`endedReason=APP_KILLED`；**只修 7 天内的**，更早的直接标 `UNKNOWN` |
| 文件消失（扫描不到） | 标 `missingAt`，**7 天宽限**后才真删（SMB 临时断连 / 移动硬盘没插都不误删）；真删时级联删 `media_streams`，progress 保留（重新出现还能续播） |
| 孤儿进度（条目已删且宽限期过） | 每 7 天清理一次：`playback_progress` 中 sourceId+mediaKey 在 `file_media_items` 里不存在的行 |
| 看完的旧片 | `completed=1 AND lastPlayedAt < now-30d` → 删 progress 行（history 仍在） |
| 历史膨胀 | 保留 90 天 / 最多 5000 条（先删最旧）；超限时按 `startedAt` 裁剪 |
| 时区/跨午夜 | `firstSeenAt` 存 UTC 毫秒；「昨日」边界由调用方按本地时区算，库里不存日期字符串 |
| 重复扫描风暴 | 同一 source 的扫描串行化（`Mutex`），并带 30s 去抖 |

## 9. 迁移（v1 → v2）与基线

1. **先决**：`exportSchema = true` + `ksp { arg("room.schemaLocation", "$projectDir/schemas") }`，把 **v1 基线**导出来并入库（`core/database/schemas/…/1.json`）。没有基线，后面的迁移测试写不了。
2. `@Database(version = 2, entities = [...新增 4 张表])`。
3. `Migration(1, 2)`：只做 `CREATE TABLE` / `CREATE INDEX`（纯增量，无数据搬迁）。**必须写**，因为 builder 没有 `fallbackToDestructiveMigration`（F1）。
4. `verifyMigrations = true`（导出后开启），并在 `core:database` 加 `MigrationTestHelper` 用例：`1→2` 后旧数据（`media_items` 若干行）仍在，新表可写。
5. 版本升级路径要覆盖「用户已装旧包 → 覆盖安装」这一个场景（真机验证，见 §12）。

> 注：`media_items` 的字段本期**一个都不改**；`file_media_items` 是全新表，所以不存在"给现有表加列导致旧行 NULL"的问题（这也是 D2 的额外好处）。

## 11. 接入本地视频时需要调整的部分

> 目标：**不加表、不改主键、不改播放页**。下面三档是按"改动量"排的。

### 11.1 零改动（设计已经预留）

| 项 | 为什么零改动 |
|---|---|
| 表结构 | `media_sources(sourceType=LOCAL, locatorType=FILE/SAF)` + `file_media_items` 直接复用 |
| 主键 | `mediaKey = local/<相对路径>` 天然成立 |
| 进度 / 历史 | `PlaybackStore` 与源无关 |
| 昨日新增 | `firstSeenAt` 由扫描器同口径写入 |
| 库页 / 详情页 / 首页 | 读的是 `MediaEntry` 适配出来的 `MediaItemDto` |

### 11.2 必须新增的实现（1 个模块 + 2 个接口实现）

| 要做的 | 说明 |
|---|---|
| `:source:local` 模块 | 实现 `MediaCatalog`：`scan()` 走 `File.listFiles`（`READ_MEDIA_VIDEO` 权限）或 SAF（`DocumentFile` + `takePersistableUriPermission`） |
| `SourceFactory.create()` 加 `LOCAL` 分支 | `sourceId="local"`，从 `media_sources.locatorBase` 取根 |
| 权限与 URI 持久化 | SAF 的 tree URI 必须 `takePersistableUriPermission` 后存进 `locatorBase`，否则重启即失效（**这是本地源唯一的新增风险点**） |
| `resolvePlayable()` | `FileLocator.LocalFile → PlaybackPlan.Direct("file://…")`；`SafDocument → "content://…"`。**不需要**走 `SmbStreamServer` |

### 11.3 需要小改的既有代码

| 位置 | 改什么 | 为什么 |
|---|---|---|
| `SourceFactoryTest` | 加 LOCAL 分支用例 | 装配点 |
| `AppModule` / `AddServerScreen` | 本地源没有「地址/账号」→ 加「选择文件夹」入口 | 添加流程不同 |
| `MediaSource.planPlayback`（仅当本地也实现 `MediaSource` 时） | 若希望本地源也能出现在现有「服务器」列表里，需要实现一次 `MediaSource` 适配；否则只走 `MediaCatalog` + 新页面 | 两种接法，**建议先只走 Catalog**，避免为了复用旧 UI 去实现一堆空方法 |
| `SmbVideoCard` → 通用 `FileVideoCard` | 抽掉 SMB 专名与"必须过代理"的假设 | UI 复用 |

### 11.4 明确不做的

- 不为本地源单独开一组表（会立刻出现两套进度逻辑）。
- 不把本地文件复制进 App 私有目录（几十 GB 不现实）。
- 不做「同文件多路径去重」（hash 成本高，收益低；重命名当新条目）。

## 13. 风险与取舍

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| 1 | **首次全量扫描**会把一万个文件的 `firstSeenAt` 写成同一天 | 首日「昨日新增」爆表（几千条） | 首次扫描（`media_sources.createdAt` 与首扫同批）标记 `firstScan=1`，该批不计入「新增」统计，UI 侧首日显示「正在建立索引」 |
| 2 | 文件 `mtime` 被保留（拷贝进来的老片 mtime 是 2019 年） | 若用 mtime 判"新增"会漏 | 本方案用 `firstSeenAt`（已规避）；`fileModifiedAt` 只作展示 |
| 3 | SMB 断连 → 扫描失败 | 若误判为"文件全没了"会清空库 | `lastScanStatus=FAILED` 时不标 `missingAt`（§7.1） |
| 4 | 重命名 = 新条目 | 旧进度成孤儿 | 本期不清理（④「一直保留」），孤儿行会积累；将来上清理策略时按 `missingAt` + 宽限期处理 |
| 5 | schema 基线缺失（现在 `exportSchema=false`） | 迁移无法测试、发版风险高 | §9 第一步就打开导出并入库 v1 |
| 6 | 时区/跨午夜 | 「昨日」口径不一致 | 边界在调用方算，库里只存 UTC ms |
| 7 | 历史与孤儿行只增不减 | 长期使用后库体积单向增长 | ④ 已确认接受；`missingAt` / `endedAt` / `lastPlayedAt` 照旧写入，将来加清理不改表 |

**用户已拍板（2026-10-27）**

| 问题 | 结论 | 对方案的影响 |
|---|---|---|
| ①「昨天新进了什么」口径 | **按首次发现（`firstSeenAt`）** | §6.3 / §6.7 不变；`fileModifiedAt` 只作展示 |
| ② 是否混排多源进度 | **不混排**：SMB 只出 SMB、Emby 只出 Emby | 所有查询都带 `sourceId = :activeSourceId`（§10 的 SQL 已是这个形状）；首页「继续观看」按当前源取，不做跨源合并 |
| ③ 音频本期粒度 | **暂不考虑兼容音频格式** —— 不扫、不入库、不统计、不展示（决策 D7） | §2.2 的 14 个视频扩展名**保持不变**；`AudioExtensions` 不扩；§12 的音频期从 P2 移出为「未排期」；`kind` 列与 `MediaKind.AUDIO` 只作预留位（本期恒 `VIDEO`，将来接音频零迁移） |
| ④ 保留策略 | **先一直保留，不做清理**，后续单独设计刷新/清理策略 | §8 的删除类任务**本期不实现**；`missingAt` / `endedAt` / `lastPlayedAt` 这些**标记字段照旧写入**（只标不删），否则将来上清理策略时没有依据 |
| ⑤ 音频之外的「多轨明细」（`media_streams`） | **仍在 P2**，与音频无关 | 它是视频的多音轨/多字幕，不依赖音频支持；是否提前到 P0 取决于「详情页是否要彻底不再读文件头」 |

> **③ 为什么保留 `kind` 列而不干脆删掉**：SQLite 加列/改列都要写迁移，而留一个"本期恒为 `VIDEO`"的列成本是零。将来 NAS 上有音频想接时，只需扩扩展名表 + 在 UI 上给音频一个播放形态，**表、主键、进度、历史、查询全都不用动**。反之若现在删掉，将来必然多一次 `Migration(2,3)`。

### 14.2 与设计的四处偏差（都记了原因，别再回头改）

1. **`media_streams` 提前到 P0**：详情页要分别渲染「视频 / 音频 / 字幕」三个分区，只存主轨汇总的话第二次进详情仍然得读文件头 —— 那 D6 就等于没落地。真机实测该条目有 2 条轨（VIDEO h264 720×480 / AUDIO mp3 2ch 44.1kHz），汇总是还原不出明细的。
2. **`probeOf()` 只在 `probeState = OK` 时返回数据**，`UNSUPPORTED` / `FAILED` 一律返回 `null`。调用方靠 `FileEntry.probeState` 区分「还没探过（去探）」和「探过读不出来（别试）」，不能靠 `probeOf() == null` 判断。
3. **`recordProbe` 用「先删后插」整体替换明细**：同一文件重探时轨道数会变（3 条 → 2 条），不删会留残留行。
4. **写入用「先 UPDATE、0 行再 INSERT」，不用 `@Upsert`**：整行覆盖会把 `playCount` 清零；`ON CONFLICT DO UPDATE` 需要 SQLite 3.24+，而 minSdk 26 的 SQLite 是 3.18。
