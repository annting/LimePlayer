# LimePlayer 相似组件（组件蔓延）审查报告

- 审查日期：2026-11-02
- 审查范围：全工程 Kotlin / Jetpack Compose 代码（排除 `build/`、测试代码、`ui-prototype/` 设计稿）
- 审查目标：找出"功能属于同一类、但实现上又有细微差异"的重复 UI 组件，评估抽象价值与重构优先级

---

## 一、背景与结论摘要

使用者在开发中观察到：项目里出现了很多"看起来是同一类、细节又不太一样"的组件。经全工程排查，结论如下：

- **规范组件库已建立且大部分界面在复用**：`core/designsystem/components/` 下的 `AppButton`、`PageHeader`、`SettingsRow` 行族、`AppConfirmDialog`、`AppChip`、`EmptyState`、`ShimmerBox`、`PosterCard`、`AppSwitch`、`AppSlider`、`AppTextField` 等是被 `docs/03-UI设计规范.md` 约束的"唯一实现"，约 **70% 的界面正确复用了它们**。
- **但仍有 8 个类别存在"功能同类、实现略异"的自定义组件**，分布在 `feature/detail`、`feature/player`、`feature/library`、`feature/settings`、`app` 等模块：
  1. 圆形 / 图标按钮（**5 套**）
  2. 分区标题 / 小标题（**4 套，其中 2 套逐字相同**）
  3. 设置项行 / 列表行（规范行族被绕过或平行重写）
  4. 主 / 次 / 文字按钮（规范 `AppButton` 被直接绕过，裸用 Material3 按钮）
  5. 对话框 / 确认弹窗（规范 `AppConfirmDialog` 仅 1 处使用，另有 3 处裸 `AlertDialog`）
  6. 空态 / 错误态（整体最健康，仅按钮未统一）
  7. 顶部栏 / 标题栏（规范 `PageHeader` 复用良好，2 处合理特化但字号不统一）
  8. 卡片封装 / 细进度条（圆角 token 混用、进度条 3 份内联重绘）

> 最值得优先收敛的是 **图标按钮（5 套）、分区标题（含逐字拷贝）、裸 M3 按钮、确认弹窗** 这四类，它们既高频又彼此不一致，且收敛成本低、收益高。

## 三、相似组件分组详表

### 组 A：圆形 / 图标按钮（最严重重复，5 套）

本质都是"带 48dp 触控热区的可点图标"，但形状、背景、按压缩放、`enabled` 表达各不相同。

| 组件 | 路径:行 | 视觉 / 热区 | 形状 | 背景 | 按压反馈 | 禁用态 |
|---|---|---|---|---|---|---|
| `CircleIconButton`（规范） | `PageHeader.kt:83` | 40 / 48dp | 默认 8dp（可覆盖） | 透明 | `pressScale` 0.95 | 无 |
| `DetailActionButton` | `DetailScreen.kt:303` | 48dp 热区 | `AppShape.circle` | filled=主色 / outline=描边 / danger=error | **无** | 无（danger 变体） |
| `PlayerIconButton` | `PlayerScreen.kt:1397` | 默认 44dp | `CircleShape` | 任意 `background` + 可选 `border` | `animateFloat` 0.9 | 无 |
| `TopBarAction` | `LibraryDetailScreen.kt:613` | 40 / 48dp | `CircleShape` | 透明 | **无** | `alpha` 0.35 |
| `BackButton` | `DetailScreen.kt:443` | 40 / 48dp | 8dp `control` | scrim 半透明底 | **无** | 无 |

**差异核心**：形状（圆 vs 8dp）、是否需要填充背景、是否分离触控热区、按压反馈（5 份里 2 份有、3 份无）、`enabled` 表达（alpha vs 无）。`DetailTopBar` 里的返回键已经改用规范 `CircleIconButton`，说明统一是可落地的。

**建议（优先级 🔴 高）**：扩展规范 `CircleIconButton`，增加可选参数 `background` / `border` / `enabled` / `shape`（它已支持 shape 覆盖），即可统一 5 处；`DetailActionButton` 的三态（filled / outline / danger）可下沉为参数或拆成 `FilledIconButton`。

### 组 B：分区标题 / 小标题（4 套，2 套逐字相同）

| 组件 | 路径:行 | 字号 | 颜色 | 上下 padding |
|---|---|---|---|---|
| `SectionTitle` | `DetailScreen.kt:782` | `titleLarge` | `onSurface` | 无 |
| `SectionTitle` | `PlayerSettingsSheet.kt:182` | `labelLarge` | `text3` | 18 / 10dp |
| `SectionLabel` | `LocalScreen.kt:728` | `labelLarge` | `text3` | 4 / 2dp |
| `SectionLabel` | `SortFilterSheet.kt:183` | `labelLarge` | `text3` | 18 / 10dp |

后三者都用 `labelLarge + text3`，仅 padding 不同；其中 **`PlayerSettingsSheet.kt:182` 与 `SortFilterSheet.kt:183` 是逐字相同的拷贝**（正文、字号、颜色、padding 完全一致）。`DetailScreen` 那份用 `titleLarge/onSurface`，属另一个层级（大标题），应保留为另一档。

**建议（优先级 🔴 高）**：抽一个 `SectionTitle(text, style = SectionStyle.Medium / Large)`，覆盖全部；直接删除 `SortFilterSheet` 那份逐字拷贝，复用 `PlayerSettingsSheet` 的同名实现或统一到新组件。

### 组 C：设置项行 / 列表行

规范 `SettingsRow` 行族被广泛复用，但以下为偏离或平行实现：

| 组件 | 路径:行 | 与规范的关系 |
|---|---|---|
| `ServerRowItem` | `SettingsScreen.kt:540` | 复用 `SettingsRow` 作底座，但**自行重写 `DropdownMenu`**（`BoxWithConstraints` + `DropdownMenu`，`SettingsScreen.kt:593`），与规范 `SettingsMenuRow`（`SettingsComponents.kt:242`，同样 `BoxWithConstraints + DropdownMenu`）是同一模式的平行实现 |
| `InfoCard` | `DetailScreen.kt:710` | 注释明说"与设置页 `SettingsGroup` 同一套语言"，但**手写**了 `clip(AppShape.card) + background(surface) + border(hairline) + HorizontalDivider`，即重造了 `SettingsGroup`（`SettingsComponents.kt:87`）的容器逻辑 |
| `LabelValueRow` | `DetailScreen.kt:750` | 独立"键 / 值"行，padding 12dp（规范 8dp），值右对齐、点击展开 |
| `TrackRow` | `PlayerSettingsSheet.kt:224` | 可选中行（label + sub + 选中态），12dp 圆角 |
| `QuickListRow` | `PlayerScreen.kt:1368` | 可选中行（label + 对勾），与 `TrackRow` 高度相似 |
| `EpisodeRow` / `FolderRow` / `AddFolderRow` | `DetailScreen.kt:512` / `LocalScreen.kt:567` / `LocalScreen.kt:535` | 各自独立的列表行 |

**差异核心**：行高（56dp vs 42dp）、分隔线（发丝线 vs 无）、对齐（左 / 右）、是否可选中。

**建议（优先级 🟡 中）**：① `ServerRowItem` 的下拉改用 `SettingsMenuRow`（或抽"行 + 下拉"基类）；② `InfoCard` 由 `SettingsGroup` 派生一个 `CardWithDivider` / `InfoGroup` 通用容器；③ `TrackRow` 与 `QuickListRow` 合并为通用 `SelectableRow`；④ `LabelValueRow` 是合理变体，可复用同一套分隔线逻辑。

### 组 D：主 / 次 / 文字按钮（`AppButton` 被绕过）

规范 `AppButton` 注释自称"全站唯一按钮"，但下列位置直接使用 Material3 原始按钮：

| 裸 M3 按钮 | 路径 | 说明 |
|---|---|---|
| `Button` / `OutlinedButton` | `LocalScreen.kt:337, :339`（`ChoiceCard`） | 主 / 次按钮未用 `AppButton` |
| `Button` | `HomeScreen.kt:990`（`EmptyHomeState`） | 空态主按钮（`RoundedCornerShape(8)` + `ButtonDefaults.buttonColors(primary)`），未用 `AppButton` |
| `Button` | `FilterBottomSheet.kt:283` | 未用 `AppButton` |
| `TextButton` | `PatternSetupScreen.kt:123` | 裸 `TextButton` |
| `TextButton` ×2 | `DetailScreen.kt:284, :289` | 裸 `AlertDialog` 内 |
| `TextButton` ×2 | `SettingsScreen.kt:520, :530` | 裸 `AlertDialog` 内 |
| `TextButton` ×5 | `LocalScreen.kt:598,658,693,698,717` | `ManageRootsDialog` 内 |

**建议（优先级 🔴 高）**：把上述裸 `Button / OutlinedButton / TextButton` 全部换成 `AppButton`（必要时加 `AppButtonStyle.Text`）。其中 3 处裸 `AlertDialog` 同时应改用 `AppConfirmDialog`（见组 E）。

### 组 E：对话框 / 确认弹窗

| 组件 | 路径:行 | 状态 |
|---|---|---|
| `AppConfirmDialog`（规范） | `AppConfirmDialog.kt:52` | 20dp 圆角、紧凑排版，已用于 `SearchScreen.kt:273`（清空历史） |
| 裸 `AlertDialog` | `DetailScreen.kt:279` | 删除条目确认——与 `AppConfirmDialog` 同义却用 M3 默认三段 24dp 布局 |
| 裸 `AlertDialog` | `SettingsScreen.kt:515` | 删除服务器确认——已手动补 `shape=AppShape.card + surface`，但仍走 M3 三段 |
| 裸 `AlertDialog` | `LocalScreen.kt:628`（`ManageRootsDialog`） | 复杂列表弹窗，标题 / 容器风格与规范不一 |

**差异核心**：圆角（20dp 规范 vs 12dp 手工 vs M3 默认）、四边内边距（20 vs 24）、按钮（`TextButton + error/primary` vs 裸 `TextButton`）。**最容易被肉眼察觉的是"内容区 → 按钮行"的留白差一倍**（用户 2026-11-02 实测反馈）：

| 间距段 | `AppConfirmDialog`（规范） | 3 处裸 `AlertDialog`（M3 默认） | 倍数差 |
|---|---|---|---|
| 标题 → 内容 | 8dp（`Spacing.sm`） | 16dp（M3 title/text 默认） | 2× |
| **内容 → 按钮行** | **12dp（`Spacing.md`）** | **24dp（M3 text 底部默认 padding）** | **2×** |
| 按钮行内按钮间距 | 4dp（`Spacing.xs`） | 12dp（M3 默认） | 3× |
| 容器四边内边距 | 20dp（`dialogPadding`） | 24dp（M3 默认；`SettingsScreen` 只改了圆角/底色，未改间距） | — |

数值来源：`Dimens.kt`（`Spacing.xs=4 / sm=8 / md=12 / lg=16`、`dialogPadding=20`）；M3 `AlertDialog` 默认走 24 体系。
证据：`AppConfirmDialog.kt:88`（标题→内容 `Spacing.sm`）、`:94`（内容→按钮 `Spacing.md`）；裸弹窗 `DetailScreen.kt:279` / `SettingsScreen.kt:515` / `LocalScreen.kt:628` 直接走 M3 默认。
> 切到"删除确认"（24dp）再切到"清空历史"（12dp），内容到按钮的留白直接差一倍——这是"弹窗看着不一样"的主因。`ManageRootsDialog` 更特殊：内容区内部用 `Arrangement.spacedBy(4.dp)` + `Divider(6.dp)`，与全站 8/12dp 节奏也不一致（同时它复用了本地 `SectionLabel`，见组 B）。

**建议（优先级 🔴 高）**：`DetailScreen`、`SettingsScreen` 两处简单确认直接换 `AppConfirmDialog`（顺带消除 12/24 差异）；`ManageRootsDialog` 是"列表型"弹窗，建议新增一个共享 `AppListDialog` 外壳（统一标题 / 容器 / 关闭按钮 / 内容→按钮间距），内部列表仍走自定义布局但统一到 8/12dp 节奏。

## 五、重构路线图建议（按优先级推进）

1. **第一轮（低成本高收益，可一次性清理）**：组 B 删拷贝 + 抽 `SectionTitle`；组 D 全量替换裸 M3 按钮为 `AppButton`；组 E 两处简单确认换 `AppConfirmDialog`。这三项不引入新抽象、纯替换，风险最低。
2. **第二轮（扩展规范组件）**：组 A 给 `CircleIconButton` 加参数统一 5 处图标按钮；组 J 让进度条复用 `CardProgressBar`。
3. **第三轮（结构性抽象）**：组 C 抽 `SelectableRow` + `InfoGroup`、收编 `ServerRowItem` 下拉；组 H 抽 `AppCard` 底座；组 I 抽 `AppBadge`。
4. **第四轮（特化打磨）**：组 G 顶栏字号统一；组 F 错误态底座。

## 六、间距基线审计（组件间间距全量普查）

> 本审计是"相似组件审查"的补充：把**组件与组件之间的空隙**全量量化，覆盖所有页面。触发点是使用者实测发现"弹窗内容↔按钮间距不统一"（已在组 E 记录），这里把同样的方法推广到全站。
>
> **判定口径**：用到 `Spacing.xx` / `Dimens.xx` 记为「规范 token」；直接写 `N.dp` 记为「裸 dp」——即使数值恰好等于某 token，也算裸字面量，等于放弃了单点修改能力。`Dimens.kt` 顶部注释要求页面严格走 **8dp 网格（4/8/12/16/24/32）**，凡不在此网格上的值标记为 **⚠️ 离网**。

### 6.4 间距整改建议（与组件收敛同步）

1. **海报网格统一 `itemGap=8`**：把 `LibraryScreen` 的 12/18 改回 8/8，与 `LibraryDetail`/`Search` 对齐（注意 `LibraryScreen` 的 18 还同时违反 8dp 网格）。
2. **所有"分组/分段之间"统一 `sectionGap=24`**：`FilterBottomSheet` 的 16、`SortFilterSheet`/`PlayerSettingsSheet` 的 18 全部改 `sectionGap`；并把 `Spacing.xl` 与 `sectionGap` 二选一，消除重复定义。
3. **底部弹层内容左右统一 `dialogPadding=20`**：`SortFilterSheet`/`PlayerSettingsSheet` 的裸 `20.dp` 改 `Dimens.dialogPadding`，与 `FilterBottomSheet` 的 `12` 二选一并文档化。
4. **标题→内容统一 `Spacing.sm=8`**：首页 10、搜索历史 6 收口到 8。
5. **页边距统一 `Dimens.pagePadding=16`**：About(18)/FolderList(20)/PrivacyGate(24)/Local 门槛(24) 改回 16，并把所有裸 `16.dp` 换成 token。
6. **激活 `itemGap`**：让"同组卡片之间"真正用 `Dimens.itemGap=8`，替换 FolderList 的 10、方案卡的 12、ManageRoots 的 4。
7. **清除离网裸值**：6/10/14/18/26/28/2/3 等改回最近阶梯值（多出的值往往是手滑，直接对齐 8/12/16/24 即可）。
8. **弹窗收敛**：3 处裸 `AlertDialog` 换 `AppConfirmDialog`（见组 E），使 `dialogPadding` 成为唯一弹窗入口。

> 注：第 1–7 项大多是"裸值改 token + 离网值对齐阶梯"的机械替换，**风险低、可批量**；真正需要决策的是第 3 项（`dialogPadding=20` vs `FilterBottomSheet` 的 12）和第 2 项（分组间隙到底 24 还是更小）——这两点建议先和设计规范 `docs/03-UI设计规范.md` 对齐再落地。
