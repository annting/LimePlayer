## 一、核验方法

对报告里 8 个组件组（A–J）+ 间距普查（§6.2 全页 + §6.3 汇总）逐条回源码核对，共抽查 **约 75 处 `文件:行` 断言**（含每一组提出的组件本身、以及 5 个页面 × 3–5 个间距数值），另外做全量 grep 复核"清单是否完整"：

| 核验手段 | 覆盖 |
|---|---|
| 按行号取原文比对 | A/B/C/D/E/G/H/I/J 全部主张组件 + 6.2 各页间距 |
| 函数体去空白后 diff | 判定"逐字相同"（组 B 的两份分区小标题 `SectionTitle` / `SectionLabel`） |
| 全仓正则统计 | `AlertDialog` / `TextButton` / `Button(` / `AppConfirmDialog` / `AppButton` / `Dimens.itemGap` / `SectionGap` / `Spacing.xl` |
| 模块依赖与可见性检查 | `feature/detail/build.gradle.kts`、`core/designsystem/build.gradle.kts`、`PosterCard` 的 `internal` 修饰 |

**结论：报告主体可信。** 行号、数值、组件清单绝大多数与代码逐字对得上，问题定位（"同类组件多套实现、弹窗间距差一倍、网格间距 8/12/18 三档"）全部成立。但有 **4 处必须修正**、**1 处只是主观估计**，其中 2 处若照报告直接施工会做不成或做错。

## 五、明确不做的项（避免无收益改动）

| 项 | 原因 |
|---|---|
| `PlayerScreen` 全量 token 化（报告标"几乎完全脱离 token 体系"） | 全屏 overlay 控件是像素级手调，改成 24/16 阶梯会直接改变画面观感，收益低于回归风险。**只做跨页不一致且肉眼可辨的那几处**（如 `:1093` 的 26→24） |
| `PrivacyGateScreen` 28→24 的全套重排 | 同上：它是独立整屏 PIN 页，28 的节奏是刻意留白；只改"与全站冲突"的页边距（T15）与按钮间距口径 |
| `HomeTopBar` 改造成 `PageHeader` 变体（报告组 G 建议） | 它是"服务器名下拉"，改造要动 `PageHeader` 的 API，收益仅是少 30 行；等 T5 完成后先看图标按钮统一的效果再定 |
| `ControlChip` 收回 `AppChip` | 播放层深色 scrim 语义不同，强并有视觉回归风险（报告自己也标了"可保留"） |
| 把 "70% 复用率" 做成指标 | 无法稳定度量，不做 |
