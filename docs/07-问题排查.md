## 1. BUG-2026-001 · LazyRow 边界回弹「停顿一会儿才弹」

| 项 | 内容 |
|---|---|
| 登记日期 | 2026-10-23 |
| 严重度 | 中（体验） |
| 发现方式 | 用户真机测试首页 |
| 影响范围 | 首页所有横向列表（继续观看、各媒体库横滑） |
| 状态 | ✅ 已解决（2026-10-23 23:12 用户真机确认「不卡顿了」，待提交；三轮才根治，见 1.7） |

### 1.1 现象

⚠️ 本段按真机手指操作的实测规律更正过（第一版是按 `adb input swipe` 的结论写的，方向反了）。

`LazyRow` 滑到最左/最右边界后松手，卡片**先停住约 500ms，之后才回弹**，不是「松手即弹」。
规律有三条：

1. **杀进程后第一次**滑到某侧边界松手 → 必卡（约 500ms），同方向之后再滑就正常；
2. 某侧卡过一次后，**换到反方向**滑也要卡；此后**每次换方向都卡**；
3. 只有「同一方向连续多次」才只卡第一次。

即：**停顿与「方向 × 首次」相关，与甩动速度关系不大**。手指慢拖到边界同样必现
（第一版记录的"慢拖正常"是 `input swipe` 的假象，见 1.7 第二轮）。

### 1.2 复现

1. 进首页 → 继续观看横滑行
2. **快速**向左甩到列表起点（或向右甩到末端），松手
3. 观察：卡片停住 → （明显等待）→ 才弹回原位

关键变量：松手瞬间的 fling 速度 `v`。
`v ≈ 0`（慢拖松手）时 `onPostFling` 立即兜底，观感正常；
`v` 大（甩动）时内层惯性 fling 持续时间长，停顿被放大到可感知。

adb 量化复现（慢拖 vs 快甩对比明显）：

```bash
adb shell input swipe 540 500 1000 500 800   # 慢拖：松手速度小，回弹立即
adb shell input swipe 540 500 1000 500 100   # 快甩：松手速度大，停顿明显
```

### 1.3 环境

- 真机 1080×2400，数据源 Emby `192.168.31.15:8096`
- 代码：`feature/library/.../home/BounceOverscroll.kt`（回弹状态机）、`HomeScreen.kt`（挂载点）
- 每个 `LazyRow` 各自 `rememberBounceOverscrollState()`，`Modifier.bounceOverscroll(state)`
  挂在 `LazyRow` 自身（`HomeScreen.kt:355-360` 继续观看、`HomeScreen.kt:495,528-532` 媒体库）——
  挂载方式本身没有问题

### 1.4 根因

**主因（三条代码事实叠加，缺一不现）**：

1. **`onPreFling` 没有吃掉 fling 速度**（`BounceOverscroll.kt:102-105`）

   ```kotlin
   override suspend fun onPreFling(available: Velocity): Velocity {
       settle(available.x)      // ① 这里已经启动了回弹 job A
       return Velocity.Zero     // ② 但返回 Zero = 不消费速度，内层照常 fling
   }
   ```

   `onPreFling` 的返回值语义是「被本 connection 消费掉的速度」。返回 `Velocity.Zero`
   意味着内层 `LazyRow` 拿到全部速度，**正常执行惯性滚动**。

2. **fling 每帧把回弹 job 取消掉**（`BounceOverscroll.kt:56-60`）

   ```kotlin
   internal fun dragBy(deltaPx: Float) {
       if (deltaPx == 0f) return
       settleJob?.cancel()      // ③ job A 活不过一帧
       offset = bounceOffsetAfterDrag(offset, deltaPx, maxStretchPx)
   }
   ```

   列表已在边界，内层每帧 `scrollBy` 的消费量为 0，剩余量全部经
   `onPostScroll(available.x)`（`:91-100`）传下来 → 每帧都调 `dragBy` → 每帧都
   `settleJob?.cancel()`。**回弹动画自始至终没跑起来**，offset 反而顺着惯性继续外推
   （这就是「松手后卡片还缓移一截」的来源）。

3. **回弹真正的起点被推到 `onPostFling`**（`BounceOverscroll.kt:107-111`）

   ```kotlin
   override suspend fun onPostFling(consumed: Velocity, available: Velocity): Velocity {
       if (offset != 0f) settle(0f)   // ④ 内层惯性滚完才走到这，job B 这才启动
       return Velocity.Zero
   }
   ```

   `onPostFling` 必须等内层 fling 彻底结束才回调。**停顿时长 = 内层 fling 的衰减时长**：
   `v` 越大 `FlingSpline` 衰减越久，3000px/s 量级约 300-500ms。

完整时序（松手后）：

```
t=0ms      onPreFling(v) → settle(v) 启动 job A；返回 Zero，内层照常 fling
t≈16ms     内层 LazyRow 惯性 fling 开始（列表已到头，剩余量逐帧外传）
fling 每帧 onPostScroll(available.x) → dragBy → settleJob.cancel() 杀掉 job A
t≈300-500ms fling 衰减结束          ← 停顿感全部来自这一段
           onPostFling → settle(0) 启动 job B，回弹这才开始
```

**次因（即使主因修好，回弹体感仍偏长）**：

`settle()` 把完整 fling 速度当 spring 初速（`BounceOverscroll.kt:77-85`）：

```kotlin
animate(
    initialValue = offset,
    targetValue = 0f,
    initialVelocity = velocityPx,   // 3000px/s 直接进 spring
    animationSpec = spring(dampingRatio = SETTLE_DAMPING, stiffness = Spring.StiffnessMediumLow),
)
```

欠阻尼 0.6 + 数千 px/s 初速：卡片先向外冲约 `v/ω ≈ 150px`，再震荡数次才停，
动画总长被拉到 1s 以上。注释里「撞墙只给 `v × FLING_KICK_RATIO`（0.02，约 60px，
`:74-75`）」的设计意图被 `initialVelocity` 覆盖放大了数倍。

另外，`kicking` 分支（`:69-76`）只在 `offset == 0` 时生效（没拖到边界但甩过去）；
实际「撞墙外推」是 fling 期间 `onPostScroll`/`dragBy` 完成的——**两条路径本来就叠在一起**，
修复时要一起理清，别只改一处。

### 1.5 修复方向（已实施 A + C）

| 方向 | 做法 | 取舍 |
|---|---|---|
| **A（推荐）** | `onPreFling` 里若 `offset != 0`（已处于过卷状态），直接 `return available` 吃掉全部速度，内层不启动 fling | 回弹从松手第一帧连贯跑完；代价是失去「松手后还跟惯性滑一截」的手感，用 `kicking` 分支补初始位移即可 |
| B | 加 `isFlinging` 标志（`onPreFling` 置位、`onPostFling` 清除），`dragBy` 在 fling 期间跳过 `settleJob.cancel()` | 保留惯性外推手感；多一个状态要维护，且要处理「拖拽中松手又立刻再拖」的竞态 |
| C（附带，无论 A/B 都该做） | `initialVelocity` 先 `coerceIn(±1200f)` 限幅再进 spring | 避免大过冲 + 多次震荡；限幅值可按真机手感调 |

推荐组合：**A + C**。改动最小、时序最干净；「撞墙」手感由 `kicking` 分支显式负责，
语义比现在「靠 fling 剩余量顺带外推」更清晰。

### 1.6 修复后怎么验

1. **adb 对比**：同一位置分别用 800ms / 100ms 两种时长 swipe 甩到边界松手，
   两者回弹启动都应无感差异（修前慢拖正常、快甩明显停顿）。
2. **量化**：松手后第一帧起 `translationX` 应单调归零，全程 ≤ 400ms；
   可用 uiautomator 量卡片 bounds 或临时打点 `offset` 变化确认。
3. **回归**：继续观看行、媒体库横滑行各验一遍；确认横滑时整页不跟着抖
   （`onPostScroll` 吃掉横向剩余量的行为不能被修复破坏）。
4. **单测**：`bounceOffsetAfterDrag` 已有覆盖；若按 A 改，补一条
   「offset != 0 时 onPreFling 返回 available」的连接层用例。

### 1.7 修复记录

**2026-10-23 修复（A + C 组合，未提交）**

改动文件：`feature/library/.../home/BounceOverscroll.kt`（唯一改动点）

1. **`onPreFling` 吃掉速度**（A）：`offset != 0` 且松手速度与位移同向时 `return available`，
   内层 `LazyRow` 拿不到速度 → 不启动 fling → 回弹 job 不再被 `dragBy` 逐帧 cancel。
   反向甩回（速度与位移反向）时 `settle(0f)` 并返回 `Velocity.Zero`，把这份速度留给列表滚回去。
2. **初速限幅 + 只取外推分量**（C）：`initialVelocity` 先取「与位移同向」的分量，再
   `coerceIn(±900)`；删掉原 `kicking` 分支（它只在 `offset == 0` 生效，修完 A 后已不可达，
   撞墙外推由 fling 期间 `onPostScroll → dragBy` 显式负责）。
3. **参数调优**（真机实测两轮）：`SETTLE_DAMPING` 0.6 → **0.72**、`StiffnessMediumLow` → **Medium**。
   0.6 + MediumLow 的实测全程 863ms（虽然不再停顿，但回弹尾巴太长），调完 450ms；
   再把阻尼提到 0.72 后 381ms，且仍保留一点过冲（不是生硬归零）。
4. `onPostFling` 仅在「没有正在跑的回弹 job」时兜底，避免把 `onPreFling` 启动的动画中途重启。

**真机验证（三星 R5CN300DNCW / 1080×2400 / Emby 192.168.31.15）**
临时打点（`println` → `System.out`）量化松手时序：

| 操作 | 松手瞬间 offset | 松手→回弹启动 | 回弹全程 |
|---|---|---|---|
| 快速甩到左边界（`swipe … 100ms`，v=6540px/s） | 181.7px | **0ms**（同一毫秒） | **381ms** |
| 慢拖到边界松手（`swipe … 800ms`，v=623px/s） | 152.4px | **0ms** | 441ms（阻尼 0.6 时）/ 后续 0.72 后同量级 |
| 甩到右边界（v=-8629px/s） | -197.9px | **0ms** | 383ms |

关键证据：日志里**没有任何 `drag CANCEL settle`**（临时打点专门抓这一条），
说明回弹 job 不再被 fling 帧杀掉。打点已在验证后全部移除。

单测：新增 `BounceOverscrollTest`（5 条）——已过卷吃速度 / 未过卷不消费 / 反向不抢速度 /
松手后归零 / 阻尼衰减与上限。注意 `backgroundScope` 里的动画**不会被 `advanceUntilIdle` 推进**
（实测 frames=0），必须 `repeat { advanceTimeBy(16) }` 手动推帧。

#### 第二轮：上面那版**没根治**（2026-10-23 22:40）

用户手测一加 Ace 5 Pro 后反馈仍有停顿，且规律很特别：

1. 杀进程后**第一次**滑到最右松手 → 卡住约 500ms 后自动回弹，之后再滑就正常；
2. 右侧卡过一次后，滑到最左也卡；**同方向多次只卡一次，换方向就一直卡**。

**真凶：平台的 overscroll 在跟我们的 `NestedScrollConnection` 抢同一份剩余量，而且平台先手。**

`ScrollingLogic` 的处理顺序是：

```
scrollBy(delta) → overscrollEffect.applyToScroll(available) → dispatchPostScroll(剩下的)
```

平台 overscroll（Android 12+ 是 `StretchOverscrollEffect` 拉伸变形）会把边界处的 `available`
**全部吃掉**去驱动拉伸，于是 `dispatchPostScroll` 传上来的 `available.x` 恒为 0 →
`onPostScroll` 开头 `if (available.x == 0f) return` 直接退出 → `offset` 永远是 0 →
松手时 `onPreFling` 的 `if (offset == 0f) return Velocity.Zero` 成立 → 我们把速度原样放给
`LazyRow` → `LazyRow` 也不 fling（已在边界）→ 最后由**平台自己的 ~500ms 归位动画**收尾。

用户看到的「卡 500ms 后自动回弹」= 平台拉伸的归位时长，不是我们的 spring。

第一轮为什么"看起来修好了"：当时用 `input swipe 100ms` 快速甩，fling 阶段
（`NestedScrollSource.SideEffect`）的剩余量偶尔能漏过平台 overscroll 落进 `onPostScroll`，
日志里就能看到 `offset≈181px`；**手指慢拖**（`UserInput`）则被平台 100% 截走，
所以只要真机手指操作就必现。这也解释了「第一次卡、换方向又卡」——平台 overscroll 为
左右两端各自维护状态，方向一换就重新走一遍拉伸建立过程。

**修复：显式禁用 LazyRow 上的平台 overscroll。**

```kotlin
fun Modifier.bounceOverscroll(state: BounceOverscrollState): Modifier = this
    .overscroll(overscrollEffect = null)   // ← 新增，其余不变
    .graphicsLayer { translationX = state.offset }
    .nestedScroll(state.connection)
```

API 语义已核对 `foundation-1.12.1` 的字节码：`Modifier.overscroll(effect)` 在 `effect == null`
时不是空操作，而是 `this then OverscrollModifierElement(null)` —— 挂一个**显式的「无 overscroll」节点**
覆盖掉上层的默认 factory，正好是「禁用」而非「不设置」。

作用域也刚好：只作用于该 modifier 节点以下的 `scrollable`（即这一行 `LazyRow`），
外层 `LazyVerticalGrid` 的竖向 overscroll 与 `PullToRefreshBox` 的 nestedScroll 都不受影响。

装到一加（PKR110 / Android 16）待用户手指验证。

#### 第三轮：前两轮都只修了「一半」，真凶在第 1.4 节没覆盖到的那条路径（2026-10-23 23:12 已解决）

第二轮装包后用户手测 7 次，反馈「只有第 5、7 次不卡」。这次改成**用户手动操作 + 我抓日志**，
一次就定位了。结论：**前两轮的修复本身没错，但只覆盖了「松手时已经过卷」这一条路径**；
`offset == 0` 时放行速度的那条分支（列表还在内容中间、用户是「甩」过去的）没人管。

日志实证（一加 PKR110，一次完整「甩到右边界」）：

```
23:06:34.831  LP2 preFling off=0.0 v=-14846    ← 松手时位移还是 0 → 放行，LazyRow 自己 fling
23:06:34.910  LP2 drag#1  delta=-91  off=-50    ← fling 撞上边界，开始把剩余量折成位移
23:06:35.000  LP2 drag#15           off=-249    ← 顶到上限（72dp）
23:06:35.0 ~ 23:06:36.4                         ← 整整 1.4s，每帧 delta≈-70~-110 反复压，
                                                   offset 已经顶死 → 画面完全静止 = 用户说的「卡住」
23:06:36.451  LP2 postFling → settle            ← 1.6s 之后才开始回弹
```

对照「不卡」的那几次，全部是 `LP2 preFling off=-179` 这种**松手时已过卷**的情形 → 立即 `settle`。

**根因（第三条路径：惯性撞边界）**：`onPostScroll` 原来不区分 `source`，
把手指拖动和 fling 滑行的剩余量一视同仁地累加。而 `LazyRow` 的 fling 撞到边界后**不会停**——
Compose 的 `FlingBehavior` 只在还能滚的时候消耗速度，撞墙后每帧把剩余量丢出来，
直到 spline 衰减完（实测 1.2~1.7s）。这段时间位移锁死在上限、回弹只能等 `onPostFling`。

用户的「第一次必卡、同方向只卡一次、换方向又卡」由此完全解释：
第一次是甩到边界的（`offset=0`），之后列表已经在边界上、松手时 `offset≠0`，走的是立即回弹那条路。

**修复：按 `source` 分流 + 惯性撞边界后主动接手。**

| 改动 | 说明 |
|---|---|
| `onPostScroll` 分流 | `SideEffect`（惯性）→ `onFlingOverscroll()`；其余（手指）→ `dragBy()` 并重置 `flingHit` |
| `onFlingOverscroll()` 新增 | 撞上边界后只累积 **3 帧（≈25ms）** 或位移到上限 **60%**（先到者），随即 `settle()`；之后这段 fling 的剩余量**只消费不再叠加**（否则每帧 `dragBy` 会把刚起跑的回弹 job 取消掉）。附带用相邻两帧的 `delta/dt` 反推撞击速度当 spring 初速 |
| `flingHit` 状态机 | `0` 未撞 / `>0` 已累积帧数 / `-1` 本次 fling 已交给回弹，避免同一段 fling 反复触发 |
| 回弹变慢 | `SETTLE_STIFFNESS` 1500(`StiffnessMedium`) → **900**：原来 72dp 位移 12 帧（**92ms**）就归零，观感是「啪一下跳回去」；现在可见行程 **≈240ms**。阻尼 0.72 → 0.70 保留约 3.8% 过冲 |
| `MIN_SETTLE_OFFSET = 1f` | 真机上出现过 `off=0.0285` 这种「非 0 但看不见」的残留，会让 `onPreFling` 走错分支、还白起一次动画，统一按 0 处理 |

**修复后日志（同设备，用户手滑 7 次）**

```
preFling off=0.0     v=-11794  → 101ms 后  settle CALL off=-96.8   ← 撞上边界立刻接手
preFling off=0.0     v= 13030  → 100ms 后  settle CALL off= 120.4
preFling off=0.0     v=-14921  →  94ms 后  settle CALL off=-125.2
preFling off=-221.15 v=-1105   →  1ms 后   settle CALL off=-221.15  ← 已过卷，立即弹
```

不再出现「顶到上限 + 1.4s 静止」的段落；100ms 那一段是 fling 从松手点**跑到边界**的正常耗时
（这期间内容在动，不是卡）。全程 `Skipped frames` = **0 条**，与第一轮结论一致：
UI 线程从未被阻塞，问题纯粹是「动画没启动」。用户确认「不卡顿了」。

单测：`BounceOverscrollTest` 补第 6 条 ——「惯性撞到边界后立刻接手回弹，不等 fling 衰减完」
（模拟 fling 一直灌剩余量、`onPostFling` 永不返回，断言位移仍要回到 0）。
全量 `./gradlew test`：**334 用例全绿**。

**三次修复的教训**：三轮里我两次都是拿 `adb input swipe` 自测就下结论，而合成手势的
速度曲线/事件流跟真手指差别很大（`input swipe` 松手速度极高、必然走「甩」路径），
正好采样不到用户实际操作的分支。改成「用户手动操作 + 抓日志对照用户口述的卡/不卡次序」
后一轮就定位了 —— 后续 UI 体感类问题一律按这个流程走。

## 2. BUG-2026-002 · 首页骨架屏「首次看不到，切 tab 回来必塌陷重载」

| 项 | 内容 |
|---|---|
| 登记日期 | 2026-10-23 |
| 严重度 | 中（体验） |
| 发现方式 | 用户真机测试首页 |
| 影响范围 | 首页冷启动、tab 来回切换 |
| 状态 | ✅ 已解决（2026-10-23，待提交） |

### 2.1 现象（两个）

1. **首次加载看不到骨架屏**——冷启动进首页直接就是内容，骨架屏一瞬而过或不可见。
2. **切到别的 tab 再切回首页**：内容闪一下 → **整页塌陷成骨架屏** → 几百 ms 后**重新加载一遍**
   （数据其实一模一样，滚动位置还归零）。

### 2.2 根因

**现象 1 不是 bug，是窗口太短。** 骨架屏代码链路完整：`HomeScreen.kt:126`
（`state.isLoading -> HomeSkeleton()`）→ `HomeSkeleton()`（`:623`，标题条 + 3 个 240×135
横滑占位 + 2×3 竖屏占位，与真实卡片同尺寸）→ ViewModel `init → load(initial = true)`。
但生产路径 `ServerHomeDataSource` 在局域网 Emby 上 4 个并发请求仅 ~100-300ms 完成；
冷启动时 Compose 首帧 + 令牌就绪本身也要几百 ms，往往首帧渲染出来时数据已到位。
证据：之前用 Mock 数据源（latency 550ms）连拍能稳定抓到骨架屏（`home-12~15` 截图）。
断网时走的是错误态（空态 2）而非骨架屏，所以也没机会看到。

**现象 2 是真 bug，根因是 `rebind` 用实例相等判定「数据源更换」**
（`AppNavHost.kt:567-580`）：

```kotlin
val data: HomeDataSource = remember(source, serverName) {          // ← 每次重新组合都是新实例
    source?.let { ServerHomeDataSource(it, serverName.orEmpty()) }
        ?: OfflineHomeDataSource("服务器连接尚未就绪，请到设置页检查登录状态")
}
...
LaunchedEffect(data) { vm.rebind(data) }                            // ← key 变 → 重触发
```

`MainScaffold` 的 `when (selectedTab)`（`MainScaffold.kt:63`）在 tab 切走时让
`HomeDestination` **退出组合**，`remember` 槽位全部销毁；切回来重新组合时
`ServerHomeDataSource(...)` 工厂重新执行，产生**新实例**（`source` 实例并未变）。
于是 `LaunchedEffect(data)` 重触发 → `vm.rebind(data)` → `data !== this.data` 判定成立 →
`load(initial = true)`（`HomeViewModel.kt:77-81`）→ **VM 层的 `isLoading = true`** →
`when` 分支整体换成 `HomeSkeleton`（内容树销毁、滚动位置丢失）→ 几百 ms 后同样数据回来。

**VM 本身是保留的**（`viewModel(key = "home-$serverId")`，owner 是 MAIN 路由的
NavBackStackEntry，tab 切换不影响），所以这不是 VM 重建，是「纯 UI 行为被误判成
数据源更换」触发全屏重载。

次因（加重但不致命）：`configs` 的 `collectAsStateWithLifecycle(initialValue = null)`
（`:560`）配合 `state.copy(isLoading = ... || configs == null)`（`:586`）。
`FileServerConfigStore.observeAll()` 是 `state.asStateFlow()` 热流（`FileStores.kt:45`），
重新收集只多 1 帧 null，影响很小，但叠加在主因之上。

### 2.3 修复方向（已实施 A + B'，见 2.5）

| 方向 | 做法 | 取舍 |
|---|---|---|
| **A（推荐）** | `HomeViewModel` 不持有 `data` 实例，改为 `load(data, ...)` 时传入（`ServerHomeDataSource` 无状态，每次新建无妨）；或 `rebind` 判定改为比对底层 `source` 引用 | 根治；`LaunchedEffect(data)` 保留也无害 |
| B | `data` 的创建上移到 `MainScaffold` 层（tab 切换不销毁），`remember` 只依赖 `source` | 同样有效；但 `HomeDestination` 就收不到「source 变了」的信号，需另传 |
| C（次要） | `isLoading \|\| configs == null` 改为首次加载标志位，消除 configs 空窗的 1 帧塌陷 | 顺手做 |

修复 A/B 后附带收益：内容树不再重建，`LazyVerticalGrid` 的 item key 稳定
（`continue-watching` / `library-*` / `recent-*`），**滚动位置自然保留**。

### 2.4 修复后怎么验

1. 首页滚动一段距离 → 切到媒体库 tab → 切回首页：**位置不变、无骨架屏闪现**
   （uiautomator 量「最近添加」标题 bounds 应与切走前一致）。
2. logcat 数 `data.load` 调用次数：切 tab 来回 10 次应**只 +0**（修复前每次 +1）。
3. 冷启动仍应看到骨架屏（这次是局域网快导致窗口短，可在 Mock 源加 latency 验证路径）。

### 2.5 修复记录

**2026-10-23 修复（未提交）**

## 3. BUG-2026-003 · 横屏播放页退场方向错误（把「内容旋转」当成「设备朝向」判断）

| 项 | 内容 |
|---|---|
| 登记日期 | 2026-10-23（第一轮误修）／二次定位 2026-10-24 |
| 严重度 | 低（体验 / 不一致） |
| 发现方式 | 用户真机测试，**两次**（第一轮修复上线后仍复现） |
| 影响范围 | 播放页退场方向；任何「用设备朝向判断本项目横竖屏」的代码 |
| 状态 | ✅ 已修（2026-10-24，待真机目视确认） |

### 3.1 现象

约定：播放页画面是横向时**向下滑出**（VidHub 的「移出滑动」），否则与其他页面一致**向右滑出**。

- 第一轮（2026-10-23）：横屏看视频返回，画面向右滑出。
- 第二轮（2026-10-24）：按「闭包捕获旧值」改完后，用户复测——**仍然向右滑**。

### 3.2 根因（第一轮判断错误，这里是更正后的结论）

播放页的「横屏」并不是设备转向，而是**把内容整体转 90°**：

```kotlin
// PlayerScreen.kt
// 横竖屏切换：**只转播放器内容，不动系统方向**（对齐 VidHub，2026-10-20）
var videoRotated by remember { mutableStateOf(false) }
val stageW = lerp(maxWidth, maxHeight, rotateProgress)
val stageH = lerp(maxHeight, maxWidth, rotateProgress)
Box(Modifier.requiredSize(stageW, stageH).graphicsLayer { rotationZ = 90f * rotateProgress })
```

好处是进出播放页没有旋转动作、也不黑闪；代价是 **Activity 与系统方向自始至终是竖屏**。
于是：

| 判断方式 | 横屏播放时的真实取值 | 结果 |
|---|---|---|
| `LocalConfiguration.current.orientation` | `PORTRAIT` | 永远 false |
| `resources.configuration.orientation` | `PORTRAIT` | 永远 false |
| `PlayerScreen` 的 `videoRotated` | `true` | ✅ 唯一可靠来源 |

第一轮把它当「闭包捕获了建图时的值」，改成在 lambda 内现读 `resources.configuration` ——
**方向对了一半**（现读确实比捕获安全），但读的源头本身就是常量，所以现象毫无变化。
用户看到的「还是向右滑」是准确的，不是缓存或安装问题。

### 3.3 修复

**① 播放页上报「画面是否横向」**（`PlayerScreen` → `PlayerRoute` → `AppNavHost`）：

```kotlin
// PlayerScreen.kt
// 判据**只看内容是否被旋转**，不看视频画幅
val landscapeContent = videoRotated
LaunchedEffect(landscapeContent) { onLandscapeChange(landscapeContent) }
DisposableEffect(Unit) { onDispose { onLandscapeChange(false) } }   // 退场后复位
```

**口径（用户 2026-10-24 真机确认）**：

| 播放状态 | 退场方向 |
|---|---|
| 竖着拿看 16:9 影片（未切横屏） | 向右滑出 |
| 主动切到横屏（内容转 90°） | 向下滑出 |

> ⚠️ 这里踩过一次**回归**：第一版判据写成
> `videoRotated || (videoWidth > videoHeight)`，想顺带覆盖「宽画幅」，
> 结果所有宽片子在竖屏下也被判成横向 —— **竖屏播放的退场全变成下滑**，用户当场发现。
> 教训：**判据宁窄勿宽**，别替用户猜口径；「看着像横屏」和「用户切了横屏」是两件事。

退场后 `onDispose` 复位，避免下次进入被误判；`onDispose` 在转场动画跑完之后才执行，
不影响本次方向。

**② 导航层用稳定的 `MutableState` 承接**（`AppNavHost`）：

```kotlin
val playerLandscape = remember { mutableStateOf(false) }

popEnterTransition = { NavTransitions.popEnterFor(initialState.destination.route, playerLandscape.value) }
// 播放页 destination：
popExitTransition = { NavTransitions.playerPopExit(playerLandscape.value) }
```

转场 lambda 捕获的是**状态对象**，在真正开始时读 `.value` —— 值实时，且不受「导航图只建一次」影响。

**③ 方向规则收敛为两条**（`NavTransitions`）：

| 场景 | 转场 |
|---|---|
| 所有页面入场 | 从右整屏滑入 |
| 推入新页（旧页） | 左移 1/4 视差 |
| 横向画面的播放页退场 | **向下**滑出，下层页面 `EnterTransition.None` 保持静止 |
| 其他页面退场 | 向右整屏滑出，下层从左侧 1/4 归位 |

入场统一从右滑入（不再按朝向分成「从下弹入」）：VidHub 就是这个组合，
也避免「点开播放整屏从下弹上来」的夸张感。因此删掉了 `exitFor`（推入播放页时旧页照常视差）。

### 3.4 教训

1. **本项目「横屏」有两个概念，永远别混**：系统方向（播放页里**从不变化**）与
   内容旋转（`videoRotated`）。判断横竖屏只能用后者。
2. **转场 / 动画 lambda 里不要捕获会变的组合值**（朝向、主题、开关）。
   安全写法：捕获 `MutableState` 读 `.value`，或读一个**真正会变**的源。
   —— 这次的真凶不是捕获，但这条依然是必须遵守的写法。
3. **判据宁窄勿宽**：宽画幅视频 ≠ 横屏播放。多一个 `||` 条件就会把用户的正常场景打坏，
   而且这种回归**只有用户能发现**（单测与自测都覆盖不到「他当时是竖着拿的」）。
4. **自测陷阱（代价最大的一条）**：我上一轮是这么「验证」的——
   `settings put system user_rotation 1` 把设备强转横屏，然后看退场方向是对的。
   但用户走的是**内容旋转**路径，设备方向根本没变，所以我造出来的是**另一条分支**，
   属于假阳性。教训：**验证要复现用户的真实操作路径**，不能自己造一个等价状态。
   （同类前科：用 `adb input swipe` 测回弹，合成手势必然走「甩」那条分支。）

### 3.5 验证

- 单测 `NavTransitionsTest` 5 条（横向播放页 → 下层 `EnterTransition.None`；非横向 / 其他页面 →
  照常水平；`playlist/1` 不被误判成播放页；空路由不判成播放页），全量 **339 用例 0 失败**。
- 真机：修复版已装（2026-10-24 00:28 构建），**退场方向待用户目视确认**。

## 4. 转场统一带来的两处回归（2026-10-24）

BUG-2026-003 修好后，统一转场暴露了两个**只在真机上才看得见**的副作用。
两者都不是「转场参数写错」，而是**页面组成**没跟上「所有页面都会滑动」这个新前提。

### 4.1 BUG-2026-004 · 冷启动时首页从右侧滑入

| 项 | 内容 |
|---|---|
| 现象 | 冷启动进 App，首页明显「从右侧滑进来」；应该直接显示 |
| 根因 | `MainActivity` 里 `servers` 的初值是 `emptyList()`，和「真的一台服务器都没有」无法区分 |
| 状态 | ✅ 已修（2026-10-24） |

时序：

```
首帧   servers = emptyList()（DataStore 还没回值）→ activeConfig = null
       → serverId = null → NavHost startDestination = WELCOME  ← 图按 WELCOME 建好
~几十ms DataStore 回值 → serverId 非空
       → startDestination 变成 MAIN → NavHost 重建导航图
       → 新首屏作为「新进入的页面」被播了一次 enterTransition（从右滑入）
```

修复：把「还没读到」和「没有服务器」分开。

```kotlin
// 用 null 表示首帧未到（Flow 是协变的，显式给 T 即可）
val servers by serverConfigStore.observeAll()
    .collectAsStateWithLifecycle<List<ServerConfig>?>(initialValue = null)

// 首帧未到就先不建 NavHost：图只会按**正确的** startDestination 建一次
if (servers != null) { AppNavHost(...) }
```

代价是一帧左右纯背景（DataStore 首帧通常 <50ms，开应用锁时还被锁屏盖住），
远好于一次假的「首页被推进来」。

### 4.2 BUG-2026-005 · 设置二级页「两层同时滑动 + 能透视到上一页」

| 项 | 内容 |
|---|---|
| 现象 | 设置 → 字幕设置 / 添加服务器：父页在左移、子页也在滑入，且子页**没背景**，两层文字叠着看得很清楚 |
| 根因 | ① 子页根布局是裸 `Column`（`AddServerScreen`、`SubtitleSettingsScreen`、`AboutScreen` 都没有 `background`），滑动时透明；② 设置子导航用了根级那套「父页左移 1/4」的视差 |
| 状态 | ✅ 已修（2026-10-24） |

修复：

1. **子页必须有背景**。设置子导航加 `OpaqueScreen`（`Surface(color = background)`）；
   根级那三个整屏页统一走 `BottomInsetScreen`，它现在同时负责「不透明背景 + 底部手势条避让」。
2. **设置子导航父页静止**：`exitTransition = ExitTransition.None`、`popEnterTransition = EnterTransition.None`，

## 5. BUG-2026-006 · 播放页控制层压在系统状态栏上

| 项 | 内容 |
|---|---|
| 登记日期 | 2026-10-24 |
| 严重度 | 中（可读性 / 误触） |
| 发现方式 | 用户真机（竖屏播放） |
| 影响范围 | 播放页所有自带 inset 的元素（顶栏、底栏、锁定按钮、提示、浮层） |
| 状态 | ✅ 已修（2026-10-24，待真机确认） |

### 5.1 现象

竖屏播放时，顶部「返回 + 视频标题」与系统状态栏（时间 / 信号 / 电池）重叠。

### 5.2 根因：inset 被上游消费，padding 恒为 0

两段代码各自都「没错」，组合起来才出问题：

```kotlin
// MainActivity：所有页面统一避让安全区
Box(Modifier.windowInsetsPadding(WindowInsets.safeDrawing.only(Top + Horizontal))) { AppContent() }

// PlayerRoute：播放页要满窗口，用负偏移把这个避让抵消掉
.layout { measurable, constraints ->
    val p = measurable.measure(Constraints.fixed(w + left + right, h + top + bottom))
    layout(constraints.maxWidth, constraints.maxHeight) { p.place(-left, -top) }
}

// PlayerScreen：再加状态栏内边距
Row(Modifier.statusBarsPadding())      // ← 实际是 0
```

`Modifier.windowInsetsPadding` 会把 inset **消费**掉：子层级再用
`.statusBarsPadding()` / `.navigationBarsPadding()` 时，Compose 会扣掉已消费的部分 ——
在播放页里正好扣成 0。于是内容原点已被抬到窗口 y=0，padding 又是 0，顶栏就压在状态栏上。

### 5.3 修复：读原始 inset（不走消费链路）

```kotlin
@Composable
private fun statusBarTopInset() = with(LocalDensity.current) {
    WindowInsets.statusBars.getTop(this).toDp()          // 原始值
}
@Composable
private fun navBarBottomInset() = with(LocalDensity.current) {
    WindowInsets.navigationBars.getBottom(this).toDp()
}
```

`WindowInsets.xxx.getTop/getBottom` 返回窗口真实 inset，**不扣消费** ——
数值正好等于 `PlayerRoute` 抵消掉的那一份。横屏旋转态系统栏已隐藏，这两个值自然是 0，行为不变。

替换范围（6 处，一次对齐，避免只修顶栏、底部手势条仍压着）：

| 位置 | 原 | 现 |
|---|---|---|
| 控制层顶栏 | `statusBarsPadding()` | `padding(top = statusBarTop)` |
| 控制层底部三行 | `navigationBarsPadding()` | `padding(bottom = navBarBottom)` |
| 锁定态解锁按钮 | `statusBarsPadding()` | 同上 |
| 直放降级提示 | `statusBarsPadding()` | 同上 |
| 拖动预览 / 连播浮层 | `navigationBarsPadding()` | 同上 |

> 通用经验：**只要某个容器用负偏移「逃出」了 insets，它内部就一定不能再依赖
> `statusBarsPadding()` 这类消费感知的 API**，必须读原始值。

## 6. BUG-2026-007 · 两种「横屏」叠加，画面变成倒立 180°

| 项 | 内容 |
|---|---|
| 登记日期 | 2026-10-24 |
| 严重度 | 中（画面不可用） |
| 发现方式 | 用户真机 |
| 影响范围 | 播放页横屏判定（布局 / 系统栏 / 退场方向） |
| 状态 | ✅ 已修（2026-10-24，待真机确认） |

### 6.1 现象

1. 竖屏播放时把手机**物理转横** → 正常进入横屏（用户认可：这是系统能力，应用只需监听）。
2. 先点控制层**旋转按钮**（内容在竖屏窗口里转 90°），再把手机物理转横 →
   画面**倒立**，相当于竖屏整体转了 180°。

### 6.2 根因：两条横屏路径同时生效

播放页有两条进入横向的路径，之前只治理了第 2 条：

| 路径 | 机制 | 归一化后的角度 |
|---|---|---|
| 物理转动（系统） | 窗口方向变横，Activity 声明了 `configChanges` 不重建 | 90° |
| 旋转按钮 | `graphicsLayer { rotationZ = 90f * progress }` 内容自己转 | 90° |
| 两者叠加 | 内容在已横过来的窗口里再转 90° | **180° = 倒立** |

补充背景：BUG-2026-003 时曾写下「不能用 `resources.configuration` 判断横竖屏」——
那句话只对**按钮路径**成立（此时系统方向恒竖屏）。物理旋转路径恰恰相反：
系统方向才是唯一真相。两条路径必须**合并**，而不是二选一。

### 6.3 修复：合并成一个「是否横向」，角度只取一份

```kotlin
// 系统方向（物理朝向）：configChanges 不重建，但 LocalConfiguration 会更新
val systemLandscape = LocalConfiguration.current.orientation == Configuration.ORIENTATION_LANDSCAPE

// 系统已横屏时，内容绝不能再转 90°；同时把按钮状态复位，
// 否则转回竖屏的瞬间画面会突然又转过去
LaunchedEffect(systemLandscape) { if (systemLandscape) videoRotated = false }
val stageRotation = contentRotationDegrees(systemLandscape, videoRotated)   // 0f / 90f

val landscapeContent = systemLandscape || stageRotation > 0f
```

`landscapeContent` 一处产出、三处消费：控制层版式（`PlayerControls(landscape = …)`）、
系统栏隐藏、导航退场方向上报。系统已横屏时**隐藏旋转按钮**（再转就是 180°，且无事可做）。

| 状态 | 内容旋转 | 布局 / 退场按横向 |
|---|---|---|
| 竖屏，没点按钮 | 0° | 否 |
| 竖屏，点了按钮 | 90° | 是 |
| 系统横屏（物理转动） | 0° | 是 |
| 系统横屏 + 按钮状态残留 | 0°（并复位） | 是 |

### 6.4 第二轮：系统方向变化时不能播旋转动画

按上面改完后，倒立没了，但用户反馈「手机转过来时屏幕上明显出现了一个旋转动画」。

原因：`animateFloatAsState` 对 `1f → 0f` 的回落同样跑 300ms `tween`。
设备已经被用户转过去了，内容再慢慢转 90° 回来，看起来就是「画面在手里打转」。

修法：**动画时长按触发来源区分** —— 系统方向变化用 `0ms`（等价瞬切），按钮操作才用 300ms。

```kotlin
val rotateProgress by animateFloatAsState(
    targetValue = stageRotation / 90f,
    animationSpec = tween(
        durationMillis = if (systemLandscape) 0 else ROTATE_ANIM_MS,
        easing = FastOutSlowInEasing,
    ),
    label = "videoRotate",
)
```

> 规律：**动画只应该服务于「用户的主动操作」**。状态被外部改变（系统旋转、恢复默认值）时，
> 播一段补间就等于让用户多看一次「已经发生过的事实」，观感上永远是多余的。

### 6.5 第三轮：残留的旋转是**系统显示层**（不做处理）

把动画状态整个摘掉后用户仍能看到旋转，据此确认这段旋转**不是 App 画的**：

- App 侧在 `systemLandscape == true` 时直接返回 `0f`，连 `Animatable` 都不创建；
- 已声明 `configChanges=orientation|screenSize|…`，Activity 不重建，所以也不是「窗口重建动画」；
- 剩下的是**显示层（SurfaceFlinger / ROM）在转整个屏幕**，任何跟随系统旋转的 App 都一样。

验证方法（5 秒）：在桌面把手机横过来，能看到同样的旋转过渡。

唯一能彻底消掉它的做法是把 Activity 锁成竖屏（`android:screenOrientation="portrait"`），
由播放页自己转内容实现横屏 —— **代价是「转手机自动横屏」这个能力消失**。
用户 2026-10-24 明确说过「物理转手机就横屏」是对的，所以**保持现状**，不做这个取舍。

### 6.6 验证

`PlayerOrientationTest` 4 条（`contentRotationDegrees` 的四种组合），
其中「系统已横屏 + 按钮状态还在 → 0°」正是这次的回归用例。全量 **343 用例 0 失败**。

## 7. 播放页方向机 + 假横屏（2026-10-24）

### 7.1 最终形态：窗口锁竖屏，只转内容

```xml
<!-- AndroidManifest.xml：全局锁竖屏 -->
<activity android:name=".MainActivity" android:screenOrientation="portrait" … />
```

- 「横屏」= 舞台 `graphicsLayer { rotationZ = 90f * p }` + **宽高对调**，`p` 由方向机驱动（300ms tween）。
- 视频、字幕、**手势层**、控制层、快捷浮层本来就在同一个舞台 `Box` 里（depth=4），
  所以整页一起转 —— 控制层位置、左右分区手势、双击 seek 方向全部自洽。
- **退出播放页时窗口方向从未变过**，没有任何旋转动作（2026-10-24 用户诉求：
  「之前假横屏，关掉视频 App 不会再转」）。

为什么最终选它（而不是 `requestedOrientation` 真转窗口）：

| | 真转窗口（方案 A） | 假横屏（最终） |
|---|---|---|
| 退出播放页 | 窗口转回竖屏，有一次旋转 | **零旋转** |
| 转向动画 | 系统显示层动画，消不掉 | 300ms 内容补间（可控） |
| 主界面 | 跟随手机 | 永远竖版（代价） |
| 画中画 | 天然正常 | 必须取消旋转（策略 A，留有黑边） |

### 7.2 状态模型（方向机，与渲染方式无关）

| 输入 | 含义 |
|---|---|
| `defaultOrientation` | 设置页「画面 · 方向」：AUTO / 横屏 / 竖屏（这个设置项此前**从未被消费**） |
| `forced` | 会话内的一次性锁定：按钮触发，或竖屏视频的默认锁定 |
| `deviceLandscape` | **自己读传感器**，稳定 400ms 才认（不看系统「自动旋转」开关，Emby 同款） |

| 场景 | 结果 |
|---|---|
| 设置 = 自动，转手机 | 400ms 后整页转 90°（假横屏） |
| 设置 = 竖屏 / 横屏 | 固定，转手机不动 |
| 点按钮（竖屏时） | 立即假横屏；**设备转到位后自动释放**，跟回设备（VidHub 手感） |
| 点按钮（横屏时） | 立即回竖屏；设备转回竖屏后释放 |
| 竖屏视频（宽高比 < 0.85） | 默认锁竖屏（抖音口径），按钮可解除 |

### 7.3 正方形视频：不锁

| 宽高比 | 例子 | 默认 |
|---|---|---|
| < 0.85 | 9:16 (0.56)、3:4 (0.75) | 锁竖屏（横过来会缩成一条） |
| ≥ 0.85 | **1:1**、4:3、16:9、21:9 | 跟随设备（横过来只会更大） |

### 7.4 三个必须的守卫

| 守卫 | 原因 |
|---|---|
| **PiP**：`fakeLandscapeActive(..., inPictureInPicture)` 返回 false | PiP 小窗按 Activity 内容渲染，转 90° 会让画面侧躺（策略 A：小窗正立、允许黑边） |
| **大屏**：`windowIsLandscape` 时不再转 | Android 16 对 targetSdk ≥ 36 的**大屏**会忽略 `screenOrientation`，窗口本来就是横的 |
| **退场方向**：`playerPopExit(landscape, fakeRotation)` | 假横屏时窗口是竖的，「画面向下」= **窗口向左**（`slideOutHorizontally { -it }`），否则看起来是「向右滑」 |
